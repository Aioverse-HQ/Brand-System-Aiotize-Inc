## How to contribute

- **Bug reports / questions** — open a GitHub Issue using the provided template.
- **Brand guideline improvements** — open a PR with changes to `docs/`.
- **New or updated tokens** — open a PR with changes to `tokens/global/` or `tokens/themes/`; never edit `tokens/build/` by hand.
- **New or updated assets** — open a PR with changes to `brand/`.
- **Package changes** — open a PR with changes to `packages/web/` or `packages/mobile/`.

---

## Branch and PR workflow

1. **Branch from `main`** — use a descriptive branch name, e.g. `tokens/update-primary-color` or `docs/improve-typography`.
2. **Keep changes focused** — one logical change per PR makes review easier and keeps the changelog clear.
3. **Open a draft PR early** if you want early feedback before the work is complete.
4. **Fill in the PR template** — link to any relevant design files, Figma frames, or issues.
5. **Require approvals** — token and logo changes require approval from both a brand designer and an engineer; documentation-only changes require one approval.
6. **Squash and merge** — the PR title becomes the commit message; keep it concise and meaningful.

## Adding or updating design tokens

Design tokens are stored in `tokens/global/` (primitives) and `tokens/themes/` (semantic mappings).

- Token files must be valid JSON conforming to the [W3C Design Tokens Community Group spec](https://design-tokens.github.io/community-group/format/).
- Never add tokens directly to `tokens/build/` — these files are generated by CI.
- After updating source tokens, run the build script locally to verify output:

  ```bash
  cd tokens
  npm run build
  ```

- Use clear, descriptive names following the existing naming conventions (e.g. `color.brand.primary`, `spacing.4`).
- Document any **breaking token renames** in `CHANGELOG.md` before merging.

---

## Adding or updating brand assets

- **Logos** go in `brand/logo/svg/` (source) or `brand/logo/png/` (raster exports).
- **Icons** go in `brand/icons/` — follow the existing SVG naming conventions.
- **Illustrations** go in the appropriate theme subfolder under `brand/illustrations/`.
- **Templates** (slide decks, social frames, press kit) go in `brand/templates/`.
- Each asset folder must have a `README.md` explaining its contents and any licensing constraints.
- Ensure SVG files are optimised (e.g. via SVGO) before committing.

## Required checks

All PRs must pass the following automated checks (see `.github/workflows/ci.yml`):

| Check | Description |
|-------|-------------|
| Lint tokens | Validates JSON syntax and token schema |
| Build tokens | Regenerates `tokens/build/` and verifies output matches |
| Docs build | Validates Markdown links and frontmatter |

## Commit message conventions

We loosely follow [Conventional Commits](https://www.conventionalcommits.org/):

```
<type>(<scope>): <short summary>

[optional body]
```

Common types: `feat`, `fix`, `docs`, `refactor`, `chore`.  
Scope examples: `tokens`, `logo`, `web`, `mobile`, `docs`.

Example:

```
feat(tokens): add color.feedback.warning primitive
```
